Little Bits of Buddha

From microservices showcase to something that actually deserves the architecture

"Could have been one lightweight process in a single container."
True. So the question is: what would make the microservices architecture not just justified, but essential? What would a Buddhabot need that a single process can't provide?

What We Have vs What's Possible

Current — Pipes & Filters
  • Telegram → pub/sub → LLM → pub/sub → Telegram
  • Stateless — every message starts fresh
  • Redis is just a message bus
  • Dapr is just pub/sub glue
  • One model, one personality, no memory
  • No awareness of who's asking
Vision — Living Teacher
  • Remembers each seeker's journey
  • Draws from searchable sutta library
  • Adapts tone: beginner vs practitioner
  • Scheduled practice reminders
  • Conversation flows as durable workflows
  • Multiple wisdom traditions, routable

Untapped Power

Redis — Not Just a Message Bus

🔍
Vector Sutta Search
Embed the Pali Canon (Tipitaka) and key commentaries as vectors in Redis. When someone asks about suffering, search semantically — not keyword match, but meaning match. "I feel stuck" finds the Sallatha Sutta (the arrow) without needing the word "suffering."
REDIS SEARCH + VECTORS
🧠
Seeker Memory
Redis state store holds each user's conversation history, practice level, and topics explored. The bot remembers: "You asked about the Five Hindrances last week — have you noticed restlessness since?" Continuity makes the difference between a chatbot and a teacher.
DAPR STATE + REDIS
⏱️
Session Rate Limiting
Redis-cell module: per-user rate limiting as a single atomic command. Prevents abuse while keeping the bot responsive. Also enables "daily wisdom limit" — encourage reflection over consumption.
REDIS-CELL MODULE
📊
Practice Analytics
Redis TimeSeries tracks engagement patterns: when do seekers ask questions? What topics recur? This isn't surveillance — it's understanding the sangha. Aggregate, anonymous, respectful.
REDIS TIMESERIES

Dapr — Not Just Pub/Sub Glue

🔄
Conversation Workflows
Dapr Workflows turn multi-step teaching into durable processes. A guided meditation isn't one message — it's a 10-minute workflow: instruction → pause (timer) → check-in → next step. Survives container restarts. Picks up where it left off.
DAPR WORKFLOWS
🎭
Dapr Actors as Seekers
Each user becomes a Dapr Actor — stateful, single-threaded, lifecycle-managed. The actor holds conversation state, practice level, preferred tradition (Theravada, Zen, Tibetan). Actor timers send daily practice reminders. Actors deactivate when idle, reactivate on message.
DAPR ACTORS
🤖
Dapr Conversation API
Replace our raw httpx calls with Dapr's native Conversation building block. Built-in response caching (same question = cached answer, saves LLM costs), PII scrubbing (strip personal details before they reach the LLM), circuit breakers, retries. The LLM call becomes infrastructure, not code.
DAPR CONVERSATION API
🔗
Multi-Tradition Routing
Dapr service invocation to route between specialized services: a Theravada service, a Zen service, a secular mindfulness service. Each with its own system prompt and sutta corpus. The user picks their path, or the system infers it from their questions.
DAPR SERVICE INVOCATION

The Combination — What Neither Can Do Alone

🪷
RAG-Powered Buddhist Teacher
The full pipeline: User asks → Dapr Actor loads their context → Redis Vector Search finds relevant suttas → Dapr Conversation API calls the LLM with context + suttas + user history → Dapr Workflow manages follow-up ("Would you like to explore this sutta further?") → Redis caches the response for common questions → Dapr state persists everything. This is the architecture earning its keep. Each piece does what it's best at. The microservices boundary isn't arbitrary — it maps to distinct concerns: user state, wisdom retrieval, LLM inference, conversation flow.

Roadmap

Phase 1 — Memory & Search
The bot that remembers
  • Dapr state store for per-user conversation history
  • Embed Pali Canon excerpts (Access to Insight, SuttaCentral) into Redis vectors
  • RAG pipeline: semantic search → context injection → LLM
  • Switch from raw httpx to Dapr Conversation API (get caching + PII scrubbing free)
  • Redis-cell rate limiting per user
Phase 2 — Actors & Personality
The bot that knows you
  • Dapr Actors: one actor per seeker, holds state + practice level
  • Actor timers: daily mindfulness prompts, practice reminders
  • Adaptive tone: detect beginner vs practitioner from conversation patterns
  • Multi-tradition routing: Theravada, Zen, secular — user picks or system infers
Phase 3 — Guided Practice
The bot that teaches
  • Dapr Workflows for multi-step guided meditations
  • Structured learning paths (Four Noble Truths → Eightfold Path → specific practices)
  • Practice journaling: user logs sits, bot tracks patterns over time
  • Redis TimeSeries for community-level practice analytics
"Why not just use one container with SQLite?"
Because a single process can't: vector-search 10,000 suttas in milliseconds (Redis), manage thousands of concurrent user sessions with automatic lifecycle (Dapr Actors), run durable multi-step meditation workflows that survive restarts (Dapr Workflows), cache repeated LLM calls to cut costs by 60% (Dapr Conversation API), or rate-limit per-user in a single atomic operation (Redis-cell). The architecture stops being a showcase when every component is load-bearing.
